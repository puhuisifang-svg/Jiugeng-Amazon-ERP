# 新品开发与候选评估联动 PRD v1.0

- 日期：2026-10-29
- 状态：待评审。本轮输出PRD，作为候选池与新品开发一起实施的依据；不代表功能已开发或部署。
- 配套：[候选池：新品开发前评估 PRD](CANDIDATE_EVALUATION_PRD_v1.0_DRAFT.md)。本篇扩展其开发承接部分，不重写候选评分、销量口径、成本公式。
- 依据：用户需求、当前development模块及前端实现、ERP-033/034、UI_STANDARD。
- 原则：候选池决定“为什么做、是否值得做”；新品开发管理“由谁做、怎么做、何时完成、如何验收”。两者使用同一条业务来源链，避免重复填报和审批后失去执行依据。

## 1. 目标、成功标准与范围

完整链路：

**来源商品/原创概念 → 候选评估 → 风险调查与复核 → 立项通过 → 开发草稿 → 方案确认 → 供应与打样 → 样品验收 → 定型风险复核 → 商品建档与交接 → 开发完成。**

项目完成必须证明：批准的关键需求已落实或经批准变更；样品通过验收；最终规格、报价和成本有版本；关联的自有商品及目标SKU明确；资料已交接。不能仅凭填写一段“打样合格”结束项目。

本期覆盖：项目责任和计划、方案与需求、供应商报价比较、多轮打样、验收、成本变化、变更审批、商品关联及双向追溯。采购下单、实际付款、入库、亚马逊发布、上市后的销售复盘不纳入本期；“开发完成”不等于已采购、已上架或产生销量。

首期建议观察的业务指标：从候选通过到接手的时长、开发阶段耗时、逾期项目数、打样轮次、最终成本相对立项估算偏差、终止原因分布。先记录必要时间与原因，不为了指标增加独立BI系统。

## 3. 业务对象与职责

- **开发项目**：一次经批准的产品开发工作；独立编号如 `ND-20261029-0001`，不依赖ASIN。既有编号保留。
- **立项基线**：候选通过时的冻结评估包，或手动项目经批准的立项资料；永久可查。
- **当前开发方案**：在立项基线上形成的可编辑方案，与来源事实分开；通过版本及差异记录演进。
- **开发要求**：客户需求、规格、改进建议及验收标准；拥有稳定编号，可追踪到候选条目。
- **供应方案/报价**：供应商及版本化报价，不等于采购单。
- **打样轮次**：一个供应商、一个方案版本对应一次送样；多供应商可各建轮次，不混写结论。
- **变更单**：对已批准范围、关键要求、经济性或计划的调整及审批。
- **验收与交接包**：最终方案、样品验证、成本、附件和商品关联的完成快照。

角色建议：开发负责人维护项目和组织验证；采购协作人员维护供货与报价；验收人员提交结果；审核人员批准立项例外、重大变更和完成；选品负责人查看并补充评估说明。权限由服务端校验，不把文本填写的“负责人”当作授权依据。

沿用现有商品读写权限为基础，新增独立审批能力及对应角色映射；默认管理员审批。自审不禁止，但必须确认并留痕；不因为是候选提交人而自动取得开发编辑权。

## 4. 候选到开发：一次录入、明确承接

### 4.1 自动创建与接手

候选“通过并生成开发草稿”在同一事务创建项目：候选通过、开发项目、立项快照、改进要求映射均成功才提交。失败整体回滚，候选保持待审核。重复请求及并发审批只能生成一个项目。

创建后开发列表显示“待接手”。开发人员点击详情确认开发负责人、协作采购人员、计划日期，再执行“开始开发”。候选负责人可以被建议为联系人，但不能自动替代开发负责人。

一候选最多一个关联开发项目；同来源确需独立开发方向时，从候选端建立明确不同的新方案及独立审批链，不解除原关联或复用旧审批。

### 4.2 交接字段映射

| 候选批准内容 | 开发承接位置 | 可修改规则 |
| --- | --- | --- |
| 候选编号、来源监控、参考商品、证据时间 | 来源与立项基线 | 只读；参考最新数据另行展示 |
| 目标客户、场景、选品理由 | 项目概览、需求说明 | 保留原文；修改目标客户/用途须变更审批 |
| 拟开发规格及图片 | 产品方案 | 生成初始方案，后续版本独立维护 |
| 必须/建议改进、验收标准 | 开发要求清单 | 逐项承接，保留来源ID与优先级 |
| 选定试算、销量假设、费用、一次性投入 | 成本与预算 | 立项估算只读，实际报价另建版本 |
| 供应建议、可接受风险、待验证项 | 供应方案、风险与验证任务 | 指定责任人、计划日期、闭环证据 |
| 评分、审核人、结论、时间 | 立项与审批记录 | 不可覆盖 |

不自动复制竞品ASIN为自有SKU，不把参考商品售价写为采购成本。币种不匹配必须显式换算并保存依据；未能映射的字段保留在评估包，不静默丢弃。

### 4.3 双向反馈

候选列表及详情显示开发编号、开发状态/阶段、负责人、计划完成日和逾期提示，点击进入项目；开发详情可返回来源候选和批准版本。

开发完成/终止/暂停更新候选的“关联开发状态”，不修改候选已通过的历史结论。终止原因回显给选品，作为后续判断依据。

评估人员后续补充证据以追加记录方式关联。开发人员看见“新增补充”，自行判断是否发起变更；不能把最新采集结果自动应用到开发基线。

## 5. 手动开发入口

保留“添加新品需求”，适合已有明确需求的内部项目；不强制填写ASIN、不伪造候选记录。

新增手动项目先为草稿，包含目标客户/需求、关键规格、目标售价与成本依据、风险、改进/验证要求、立项理由。可引用同一套候选评估字段和成本组件，避免另建一套评分与费用逻辑；不强制五维评分，但立项依据和风险判断不可空缺。

手动项目提交立项后锁定送审版本，审核人通过/退回/终止。通过后才可开始开发。若机会尚不明确，提供“前往候选池新增候选”引导，不同时自动创建两份单据。

这是对ERP-034中新建草稿即可开始开发规则的调整。历史进行中项目保留原流程资格，标记历史立项，不补造审批；新项目采用本规则。

## 6. 生命周期与阶段门槛

### 6.1 主状态

| 状态 | 说明与操作 |
| --- | --- |
| 草稿/待接手 | 候选来源已立项；手动来源显示未立项/退回意见；完善负责人计划 |
| 待立项审核 | 仅新手动项目；审批或撤回，提交版本只读 |
| 开发中 | 维护方案、报价、样品及验证；按当前阶段推进 |
| 待完成审核 | 完成包已冻结，审核人通过或退回开发中 |
| 已暂停 | 保留暂停前状态/阶段、原因、责任人、计划恢复日期；可恢复或终止 |
| 已完成 | 完成快照只读，可查看商品及历史 |
| 已终止 | 保留原因、已投入和结论，只读；历史VOID显示“已终止（历史作废）” |

暂停限草稿/开发中；审核中先撤回再暂停，避免出现悬空审批。暂停期间可追加沟通记录，不能编辑已批准方案或推进阶段。恢复回到暂停前状态，日期调整须留原因；计划到期不会自动恢复。终止未完成项目须填写原因并由审核权限确认；有待审单据时一并结束并保留记录。

候选来源无需重复立项审批；所有项目完成均需明确验收审批。已完成/已终止不直接重开，后续新工作另建项目并引用原记录。

### 6.2 开发中五个阶段

| 阶段 | 主要工作 | 推进条件 |
| --- | --- | --- |
| 方案确认 | 明确目标规格、必须要求、验收标准、负责人、计划与投入预算 | 立项有效；关键要求有验收方法；影响成本/可制造性的关键规格已明确；风险有责任人 |
| 供应与打样 | 比较报价、确定供应方案、登记样品及进度 | 有选定供货方案和有效报价/依据；至少一轮样品已收到并可验收 |
| 样品验证 | 对照要求逐项测试，记录缺陷、整改和复测 | 必须要求全部通过或经批准变更；无阻断风险，选定最终样品 |
| 定型风险复核 | 以最终样品、结构外观、品牌、包装、说明书和已有销售素材复核知识产权及类目要求 | 各目标市场调查已复核，疑点/整改闭环；授权范围有效；未完成材料有明确处理边界 |
| 定型与建档 | 冻结规格、复核成本、关联商品/SKU、完成资料交接 | 定型风险复核通过，最新方案、验收、报价与商品映射一致；完成检查通过后送完成审核 |

允许准备工作交叉进行，例如方案阶段收集报价；阶段表示当前主要进度，不禁止维护后续资料。回退阶段需填写原因，已有结果保留；涉及要求或定型变更时原验证标记“需复核”，不能带旧通过结论直接完成。

免实体打样仅为明确例外：例如仅包装文案调整。填写原因和替代验证方式，审核人员批准后采用同一要求清单验收；不能开发负责人自行勾选跳过。普通实体新品默认必须打样。

## 7. 项目计划与开发要求

项目字段：名称、目标市场、产品类别、开发负责人、采购协作人员、优先级、计划开始/完成日、目标开售日、预计一次性投入上限、首批数量及假设、概述。开售日期为计划，不代表系统发布商品。

- 开始开发需有效立项、开发负责人及计划起止日；结束日不早于开始日，开售日如填写不能早于计划完成日。
- 各阶段可设计划完成日，默认不强制填写复杂甘特图；自动记录实际开始/结束时间。
- 逾期=未完成/终止且当前日期超过计划完成日；暂停时展示暂停和计划已过期，不暗中顺延日期。
- 内部业务日期采用Asia/Shanghai，与亚马逊商品观测的来源时区分别标注。

开发要求每行：要求编号、来源需求、修改内容、必须/建议/后续、目标规格、验收方法、量化阈值或可判定条件、责任人、计划日期、状态、证据。

状态为待处理/处理中/待验证/已通过/未通过/批准取消。只有测试结果或批准的例外能满足完成门槛；备注“已完成”不能代替验证。建议项未做须写处置结论，后续项进入交接清单而非静默消失。

## 8. 供应方案与报价

支持同项目多个供应商方案，引用已有供应商档案；尚未建档时允许临时供应商名称和联系人说明，标识“未建档”，后续由采购流程建立正式档案。

报价字段：供应商、对应方案版本、适用规格/变体、报价日期、有效期、采购单价及币种、税费/运费包含范围、MOQ、价格阶梯（可选）、打样费、模具费、样品周期、大货周期、付款条件说明、附件及备注。

- 报价只保存商业依据，不触发付款或采购。
- 对比时明确含税、币种、交付范围和数量档位，不直接将不同口径价格排序为“最便宜”。
- 选定一个主供货方案，可保留备选；更换方案保留历史和理由。报价变更产生版本，不覆盖已被验收或成本引用的报价。
- 过期报价提示复核；用于定型的报价必须有效，或有供应商确认延用的日期及证据。
- 自研/自制允许内部制造方案，登记材料/人工等估算或已有成本来源，不强制虚构外部供应商。

## 9. 打样与验收

### 9.1 多轮打样

每轮自动编号，绑定供应方案及产品方案版本；保存请求日期、预计到样日、实际到样日、数量、样品标识、费用、图片/文件、测试人和结论。

轮次状态：待寄样→在途→已收样→验证中→合格/需整改/不合格；可取消但须原因。样品返工或再次送样建立新轮次，引用上一轮缺陷，不抹去失败结果。

### 9.2 验收清单

验收项从开发要求生成，允许增加实际测试项。每项包含标准、实测结果、通过/不通过/不适用、测试日期、测试人、证据和缺陷等级。不适用必须写原因，关键项须审核确认；未测试不能视为通过。

缺陷记录：现象、照片、影响要求、严重程度、整改责任人、计划完成日、复测结果。阻断缺陷未关闭不能定型；非阻断问题可明确接受并形成交接任务。

选定“最终样品”时核验其方案版本与当前方案一致。后续改材质、尺寸、结构或供应商时，受影响测试自动标记待复核，由开发负责人确认复测范围，审核人审查；不能复用不匹配版本的合格状态。

## 10. 成本复核与预算

复用候选池的费用模型、汇率口径、贡献利润及敏感性公式，不另建相冲突的“净利润”算法。

成本页并列三列：立项估算、当前选定方案、最终确认版本。每行显示费用、原币和折算金额、依据/报价日期、变化额及变化率；立项值为0或未知时不计算百分比，显示新增费用或不可比较。

- 有效供应商报价可由用户选择带入采购成本，预览差异后确认，不自动覆盖。
- 展示采购、包装、物流、平台、广告、售后等单位费用；单独展示打样/模具等一次性投入、已登记投入和预计剩余投入。
- 已登记投入为项目管理记录，说明是否已支付/待支付/估计；不宣称与财务实付一致。
- 目标月销量沿用批准假设并可版本化调整，不用竞品销量冒充我方订单预测。
- 送完成审核必须选择一个完整最终成本版本；物流等尚不能确认的项目可保留有依据的估算，突出假设和敏感性，不能显示为已确认真实费用。
- 初期不自动同步自有SKU的生效成本价，避免把评估估算发布为正式成本；如需建正式成本方案，进入现有成本模块人工复核。

## 11. 方案变化与重新确认

保存日常工作记录不需要审批。以下变化在应用前生成变更单：

1. 目标客户/用途、关键功能或必须要求删除/降级；
2. 关键材质/尺寸/结构、定型后供应商变化；
3. 目标售价下降、单件成本上升、利润恶化或一次性预算超出批准值；
4. 已批准计划完成日推迟、关键风险处置方案改变。

首期不引入复杂可配置阈值。经济性相对当前批准成本版本出现上述不利变化时要求一次重新确认；报价收集草稿可自由编辑，选择其为执行/定型方案时才校验，不因每次录入反复弹审批。

变更单展示：原值/新值、原因、关联需求及证据、成本/进度/验证影响、申请人和审批意见。审批通过才生成新的执行基线，立项原快照仍保留；驳回保留原执行版本。相同项目同一时间最多一张待审关键变更，冲突时提示先处理旧单。

送完成审核时不得有未处理的关键变更。变更获批后，对受影响的验证项重新确认；未受影响项保留并标明适用版本。候选池只追加“开发发生已批准变更”的摘要，不回写原候选结论或重新建开发单。

## 12. 商品建档与完成交接

### 12.0 亚马逊风险复核（开发必经步骤）

2026-10-29增补，与候选PRD §7.1使用同一调查类型、证据结构和结论；独立增加“风险评估”页签及“定型风险复核”阶段。立项初筛解决是否值得投入，定型复核检查实际做出的产品及拟用材料，不能仅继承竞品或早期概念的结论。

- **承接初筛**：接收各目标市场的商标、版权、外观及功能结构专利调查报告、权利命中项、授权范围和未到执行时点的类目验证任务。候选初筛快照只读。
- **复核实际方案**：关联最终方案版本和样品；检查品牌/Logo、外观、结构功能、包装图案、说明书、产品图片、文案及已准备的A+内容/视频。每项注明原创/委托创作/获许可/未确定及证据。
- **触发时点**：进入开发时确认初筛仍适用；开模等高投入前，对涉及的外观/结构权利疑点须先闭环；定型前必须完整复核。增加市场、改结构外观/用途/品牌/素材、更换供应方案或许可到期/撤回时，受影响项变为待重新评估，并阻断受影响阶段推进。
- **调查过程**：支持检索记录、权利信息、产品对照、调查人、复核人、日期及专业报告附件。实际疑点由有相应能力的专业人士复核，系统不自动断言侵权或保证不侵权。
- **处理路径**：补充授权、整改方案、专业复核、终止开发；整改可能影响成本/交期/样品，必须关联变更单及必要复测。仅写“已修改一点”不能自动关闭疑点。
- **放行条件**：所有适用市场及调查类别已复核，结论为范围内初筛未发现明显风险/适用授权已核对/有依据的不适用；无待复核疑点、待整改或不可接受项。高利润、供应商承诺和普通风险接受意见不能越过此门槛。
- **未准备的上架素材**：列明尚未制作的Listing文案/A+或视频，不对其出具已检查结论。可完成产品开发，但完成包必须显著标记“未覆盖素材待上架前核查”，指定责任人，并生成交接检查项。若产品自身图案、包装、说明书等必要交付件缺少权利依据，则不得完成。
- **平台与类目**：定型前应完成适用于当前产品的测试/证明材料核验；只有确需在上架阶段完成的账号/平台提交流程可作为交接项。当前产品实质合规缺口不能作为“上架再处理”绕过完成审核。
- **交接边界**：本期不执行亚马逊上架，交接检查项不声称能技术上阻止卖家后台发布。后续接入上架流程时应复用放行结果并检查新素材、目标市场和有效期。

风险结果与当前方案版本绑定。旧版本/过期授权不能用于新版本放行；专业报告和素材许可受权限控制。完成后收到新的侵权线索或许可失效，追加“需重新核查”风险提醒并通知对应业务负责人（系统内任务），保留历史完成事实，不自动删除项目或下架商品。

### 12.1 关联规则

每项目首期对应一个自有产品父体，可包含多个SKU，逐项指定本项目涉及的SKU及其方案/样品覆盖关系；不能因为父体已有其他SKU就把所有SKU算成本次开发成果。一个SKU与其他项目重复关联时提示已有关系并要求说明，不能静默覆盖旧关联。

可选择已启用产品/SKU，也可通过“去建立商品档案”打开现有商品管理流程。首期不自动生成商品或SKU；页面提供可复制的定型资料清单，建档后返回项目选择关联。避免为了建档便利在本轮扩张产品主数据写入接口。

### 12.2 完成检查

必须满足：

- 所有必须要求已通过或有批准取消记录；建议/后续要求有明确处置。
- 最终样品合格或已批准替代验证；无阻断缺陷和关键未判定风险。
- 定型风险复核已通过，当前版本的知识产权疑点已闭环，必要交付素材授权及类目要求有依据；未覆盖的上架素材明确列为交接待核查项。
- 最终规格、供应方案、报价、完整成本版本已选定，彼此版本一致。
- 关联启用的自有商品和至少一个本次目标SKU，关键规格差异已核对。
- 交接资料齐备：定型规格、图片/图纸（适用时）、包装说明、供货信息、验收标准及结果、成本依据；不适用项写原因。
- 每个未关闭但可接受事项有负责人、计划日期及交接说明。

点击“提交完成审核”冻结完成包。审核人通过后标记已完成，记录实际完成时间和审批版本；退回则回到开发中指定阶段，填写原因。待完成审核期间修改内容必须先撤回，避免审核到一半数据变化。

提交时和审批通过时均核验关联商品/SKU仍存在且启用。完成后若商品停用，历史完成保持，界面提示当前档案已停用，不回滚历史项目。

## 13. UI设计

遵循现有UI_STANDARD，候选和开发使用同一密度、状态、证据、成本与版本展示组件。不是简单把所有字段放在一张长表里。

### 13.1 新品开发列表

面包屑：**商品 / 产品管理 / 新品开发**。

状态页签：全部、待接手、待立项审核、开发中、待完成审核、已暂停、已完成、已终止。待接手为草稿业务显示；手动草稿单独标注未立项。

筛选：名称/编号/来源候选/ASIN/SKU关键词、负责人、采购协作人员、来源、当前阶段、优先级、计划日期、仅逾期；点击搜索才执行，支持重置。

工具栏：“添加新品需求”、有选择时可用的“分配负责人”“导出项目摘要”。不提供批量完成/批量批准。

列：勾选、图片、项目名称/编号、来源候选、状态、当前阶段、开发负责人、采购协作人员、必须要求通过数/总数、最终样品状态、风险复核状态、目标售价、当前贡献利润、计划完成日、逾期天数、操作。

左固定项目身份，右固定详情操作，中间TableViewport横滚，底部ListPagination固定；完成进度使用可解释的“已通过必须要求 4/6”，不用未定义的综合进度百分比。

### 13.2 开发详情

面包屑：**商品 / 产品管理 / 新品开发 / 开发详情**；新品开发可返回并保留筛选。

顶部摘要：图片、名称/编号、状态、来源候选、负责人、计划完成日；阶段条展示方案确认→供应与打样→样品验证→定型风险复核→定型与建档，每阶段可点开对应内容。顶部操作按权限和状态展示：编辑、推进阶段、提交完成审核；暂停/终止等放次级菜单。

四项概览：当前阶段及停留天数、必须要求通过数、当前成本/贡献利润、交期与风险。没有结果时显示待补充，不展示假百分比。

| 页签 | 布局与主要内容 |
| --- | --- |
| 项目概览 | 目标客户与机会、来源评估摘要、责任及日期、待办/阻断事项、里程碑、商品关联 |
| 产品方案 | 立项基线/当前方案对照、规格、开发要求、优先级、验收标准及差异 |
| 供应与打样 | 供应方案对比表、报价版本；样品轮次时间线，打开轮次查看验收清单与缺陷 |
| 成本与利润 | 立项/当前/最终成本对照，敏感性及一次性预算，复用候选试算控件 |
| 风险评估 | 初筛与定型报告对照，商标/版权/专利调查，素材授权、类目要求、整改和复核；明确市场、方案版本和覆盖范围 |
| 验收与交接 | 完成检查清单、最终样品、资料包、商品/SKU关联、送审与验收结论 |
| 变更与记录 | 变更单原值/新值对照、审批、阶段、暂停及终止历史；可查立项与完成快照 |

证据在条目旁查看，统一附件抽屉按规格/报价/样品/验收分类。现有附件能力复用；报价及附件按权限访问，不默认公开链接。

编辑使用统一抽屉或弹窗，正文一个主滚动区，保存/取消固定可见；未保存离开提示，失败保留输入，图片contain可预览。重操作按钮展示进行中与结果，后台失败给可重试提示。

桌面1280×800：方案并排、费用表与结果并排；800×600：卡片堆叠、保留工具栏；360px：摘要卡片化、表格局部横滚、详情页签可横滚。不能靠缩小字体或裁切操作列适配。

## 14. 端到端示例

1. 选品从上新监控发现商品，加入候选；发现目标用户反馈“收纳后体积大”。
2. 候选提出折叠结构改进，明确收纳尺寸目标、测试方法及预估增量成本；完成评估审核。
3. 系统创建开发草稿，改进项作为必须要求进入项目，无需开发人员重新抄写。
4. 开发负责人接手，两家供应商报价；选择其中一家并登记第一轮样品。
5. 第一轮折叠强度测试失败，记录缺陷，调整连接结构并发起方案/成本变更审批。
6. 变更通过后登记第二轮样品，复测相关项目，选为最终样品。
7. 对改进后的最终结构、外观、品牌及包装做定型风险复核；疑点闭环后复核最终成本，建立/关联自有产品与目标SKU，提交完整交接包。
8. 完成审核通过，候选详情显示“开发已完成”及商品入口，原评估和失败样品仍可追溯。

此示例为设计场景，不代表已发生的业务数据。

## 15. 技术契约与兼容

- 两模块共享字段定义与前端组件，不互相依赖内部表结构；selection发布公共批准事件，development使用公共商品/供应商查询接口。
- 候选批准事务涵盖开发草稿及完整基线，已有开发记录不重复创建；附件引用不复制公开文件，不扩大原访问权限。
- 主状态、开发阶段、审批单、要求条目、样品结果各有独立语义。不能仅用一个状态字段表达所有进度。
- 幂等请求覆盖创建、审批、阶段转换及完成；所有修改执行版本校验，过期审批返回冲突，禁止静默覆盖。
- 新状态只新增兼容映射：历史DRAFT显示待接手；IN_PROGRESS显示开发中并标“阶段待确认”，由用户补充阶段，不自动宣称已打样；COMPLETED保持历史完成；VOID保留历史作废原因。
- 历史已完成项目不因缺新验收项重新打开；历史进行中项目下次完成时需按新清单补充或由审核人批准明确的历史资料例外，不补造样品或审批记录。
- 历史文本供应说明、样品记录、研究说明保留为“历史记录”，不强行解析成已验证结构化数据。
- 旧候选来源ASIN非空假设需解除，兼容非亚马逊候选、独立候选编号和一项目多目标SKU。
- 不自动重写自有商品规格或正式成本；后台任务失败不清空业务数据。

## 16. 联合实施范围和顺序

候选池与新品开发作为一个完整业务版本规划，建议按可验证纵向流程实施：

1. **统一基础**：身份、来源、多种产品、规格/证据/费用定义、权限和状态迁移。
2. **评估到立项**：四来源入池、评估UI、需求与改进、成本和审核；一次事务生成完整开发基线并双向跳转。
3. **开发执行**：接手与计划、阶段、报价、打样、验收、成本差异、变更审批。
4. **定型闭环**：商品/SKU关联、完成审核、候选反馈、旧数据兼容和全链路回归。

中间阶段可局部验收，但不能以“能创建草稿”宣布整套闭环完成。用户批准开发后，沿用原本地环境部署验证；提交/合入main及公网发布继续等待用户明确指令。

首期不包含自动采购、付款、入库、自动生成/发布Amazon Listing、自动建立商品、正式SKU成本发布、复杂甘特图、外部供应商协作门户及上市绩效回流。保留接口边界，不展示空功能。

## 17. 联合验收标准

| 编号 | 验收场景 |
| --- | --- |
| D01 | 候选四种来源均能通过审核生成开发草稿，非亚马逊无ASIN不报错 |
| D02 | 候选通过、基线和开发项目原子提交；并发/重试不重复；失败候选仍待审核 |
| D03 | 需求、规格、改进、成本及风险完整交接，候选/开发相互定位且显示最新关联状态 |
| D04 | 源商品更新不会覆盖立项基线或开发方案；已批准变更也不改原候选快照 |
| D05 | 新手动项目未立项不可开始；候选项目无需重复立项；角色权限和自审记录正确 |
| D06 | 阶段门槛在服务端执行，暂停/恢复/终止不丢数据，审核中不能直接修改送审版本 |
| D07 | 多供应商报价、含税币种差异、报价有效期及选定方案可追溯，不触发采购 |
| D08 | 多轮打样保留失败记录；必须要求未通过阻断定型；改版后受影响测试需复核 |
| D09 | 成本变化显示差额，未知与0分开，换币/敏感性和候选公式一致，不重复计费 |
| D10 | 不利成本/关键方案变化经审批后才生效；重复或过期审批不覆盖当前方案 |
| D11 | 完成前必须检查最新方案、样品、成本、资料和目标SKU；关联停用阻断审批 |
| D12 | 完成只更新开发与关联显示，不自动创建库存/采购/平台Listing或发布正式成本 |
| D13 | 历史候选、项目、文本记录及编号完整保留，不补造新流程的验收证据 |
| D14 | 桌面/窄屏/手机均可查看全部信息并完成操作；未保存保护、错误重试、分页正常 |
| D16 | 初筛通过不等于定型放行；结构/品牌/市场变化使相应调查待复核，未闭环禁止推进与完成 |
| D17 | 授权范围、期限与当前方案一致；供应商声明和无检索命中不能自动生成安全保证；非亚马逊及手动项目同样调查 |
| D18 | 必要包装/说明书风险未闭环禁止完成；尚未制作的上架素材明确显示未覆盖并进入交接，不冒充已审核 |
| D15 | 真实端到端验收覆盖：监控入池→评估→退回补充→通过→打样失败→变更→复测→建档关联→完成审核→候选回看 |

研发门禁：受影响前后端完整质量检查、迁移与重启、审批事务回滚/幂等/并发/权限测试、真实浏览器三视口与完整链路验收；验证只使用合成资料。本PRD阶段不运行无代码变更的构建测试，不宣称上述能力已上线。

## 18. 建议采用的默认规则

- 候选审核通过自动生成开发草稿，开发负责人确认后开始。
- 一候选对应一开发项目，一项目对应一个自有产品及多个明确目标SKU。
- 实体新品默认需要样品验收；免打样必须批准替代验证。
- 成本和关键方案发生不利变化需重新确认，不能悄悄偏离批准依据。
- 开发完成经过验收审批，完成与采购/上架分开。
- 两份PRD合并作为一个开发范围推进，先本地验证，暂不提交main。

本轮风险评估增补的官方来源及法律类型说明统一见[候选PRD §15](CANDIDATE_EVALUATION_PRD_v1.0_DRAFT.md#15-风险评估设计参考)。首期为人工调查与证据管理，不包含自动法律判断或采购专业调查服务。
