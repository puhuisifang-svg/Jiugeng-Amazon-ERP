# 九更亚马逊 ERP 项目规划方案

> 状态：Superseded。首期业务范围已根据老板确认调整为产品、辅料/物料、生产及选品监控，当前评审基线见 [首期范围与实施规划 v0.2](PHASE1_SCOPE_PLAN.md)。本文保留为原始宽范围规划记录。

> 版本：v0.1（评审稿）
> 日期：2026-09-12
> 项目名称：九更亚马逊 ERP
> 使用对象：公司内部 Amazon 运营、采购、仓库、物流、财务及管理人员

## 1. 项目结论

本项目拟建设一套面向公司内部、自研自用的 Amazon ERP 管理系统，目标不是首期完整复制赛狐或领星，而是先打通公司最关键的业务与数据闭环：

**Amazon 店铺授权与数据同步 → 商品/订单/库存 → 采购/入库/发货 → 成本/利润/回款 → 经营看板与异常预警。**

建议采用“Amazon 优先、内部流程优先、数据可信优先”的策略：

1. MVP 只支持 Amazon，不在首期扩展其他电商平台。
2. 优先替代高频 Excel、人工下载报表和跨部门重复核对。
3. 首期采用模块化单体架构，不提前拆成大量微服务。
4. 所有关键财务指标必须能追溯到原始数据、业务单据和计算规则。
5. Sprint 以交付物验收为准，文中的周数只用于资源和节奏预估。

在需求边界稳定、Amazon 授权顺利且核心岗位能持续参与验收的前提下，建议 MVP 目标周期为 **16～20 周**。

## 2. 建设背景与目标

### 2.1 背景

赛狐、领星等成熟 Amazon ERP 已覆盖运营、广告、供应链、财务和 BI 等完整链路。内部自研的价值不在于功能数量，而在于：

- 与公司现有组织、审批和核算规则深度匹配；
- 统一多店铺、多站点和多仓数据口径；
- 减少 Excel、人工报表下载和重复录入；
- 将关键经营数据沉淀为公司自有数据资产；
- 支持后续按公司策略建设自动化与 AI 能力。

### 2.2 项目目标

- 建立统一的店铺、站点、SKU、MSKU、ASIN、FNSKU、仓库和供应商主数据。
- 自动同步 Amazon 订单、Listing、库存、费用、结算和报告数据。
- 打通采购、入库、库存、FBA 发货和成本流转。
- 形成订单利润、SKU 利润、店铺利润和结算回款的统一口径。
- 为管理层、运营、供应链和财务提供角色化看板与预警。
- 建立权限、审批、审计、数据质量和异常补偿机制。

### 2.3 首期非目标

- 不做对外售卖的 SaaS 产品，不建设租户计费和开放市场。
- 不追求首期覆盖 Temu、TikTok Shop、沃尔玛等多平台。
- 不在 MVP 阶段自建完整 WMS、TMS、CRM 或会计总账系统。
- 不在基础数据未稳定前上线自动调价、自动否词等高风险自动化。
- 不以界面和功能数量对标成熟商业 ERP，优先保证关键流程可用、数据准确。

## 3. 用户与权限角色

| 用户角色 | 核心诉求 | 主要权限 |
| --- | --- | --- |
| 管理层 | 查看销售、利润、库存、现金与异常 | 全局看板、报表、审批、审计查询 |
| 运营 | 管理 Listing、订单、销量、库存和广告表现 | 按店铺/站点授权的数据查询与操作 |
| 采购 | 采购计划、采购单、供应商与到货跟踪 | 采购及供应商模块 |
| 仓库 | 收货、质检、入库、出库、盘点 | 指定仓库作业权限 |
| 物流 | FBA 发货、头程、物流费用和轨迹 | 发货与物流模块 |
| 财务 | 成本、费用、利润、结算和回款核对 | 财务全模块及封账权限 |
| 系统管理员 | 组织、账号、角色、店铺授权、配置 | 系统配置与审计，不默认拥有业务审批权 |

权限模型采用 **RBAC + 数据范围**：功能权限控制“能做什么”，数据权限控制“能看哪些部门、店铺、站点和仓库”。敏感操作必须记录操作前后值。

## 4. 产品范围与优先级

### 4.1 P0：MVP 必须具备

#### A. 系统基础

- 组织、用户、角色、菜单和数据权限
- 店铺与站点管理、Amazon SP-API 授权状态
- 操作日志、登录日志、数据变更审计
- 任务中心：同步任务、失败重试、异常告警
- 基础配置：币种、汇率、时区、税率、费用类型、核算规则

#### B. 主数据

- 商品/SPU/SKU 管理
- SKU、MSKU、ASIN、FNSKU 映射
- 店铺、站点、仓库、库位、供应商、物流商
- 组合商品和包装关系（如公司业务需要）
- 主数据导入、校验、冲突提示和修改历史

#### C. Amazon 数据中心

- Orders：订单、订单项、状态、退款/取消基础信息
- Listings/Catalog：Listing 和商品目录信息
- FBA Inventory/Reports：可售、预留、在途及库龄相关数据
- Finances/Reports：交易、费用、结算和回款数据
- Feeds：后续批量更新 Listing、价格或库存的统一出口
- Notifications：可用事件的实时通知；其余数据采用定时增量同步
- 原始报文留存、标准化映射、幂等、限流、重试和补数

#### D. 销售与库存

- 多店铺、多站点订单统一查询
- SKU/ASIN/店铺/站点维度销量统计
- 本地仓、在途、FBA 库存统一视图
- 库存流水、库存调整、盘点和差异处理
- 缺货、低库存、超龄、滞销和异常变动预警

#### E. 采购与 FBA 发货

- 采购计划、采购单、审批、到货和关闭
- 供应商档案、交期、价格与到货表现
- 收货、质检、入库和采购差异
- 补货建议基础版：销量、可售、在途、安全库存、采购/运输周期
- FBA 发货计划、装箱、发运和状态跟踪
- 头程物流单与费用登记

#### F. 财务与利润

- 采购成本、头程、平台费、广告费、退款及其他费用归集
- 订单利润、SKU 利润、店铺利润和站点利润
- 汇率与费用分摊规则可配置
- Amazon 结算单、回款状态和差异核对
- 数据封账、反封账授权、计算版本与来源追溯
- 利润报表可下钻至订单、交易和原始报告

#### G. 经营看板

- GMV、订单量、销量、毛利、毛利率、退款率
- 库存金额、周转天数、缺货风险和滞销金额
- 店铺、站点、品牌、产品负责人和 SKU 多维筛选
- 同比/环比、目标对比和异常提示
- 报表导出与权限水印

### 4.2 P1：MVP 稳定后建设

- Amazon Ads 授权、SP/SB/SD 广告数据与广告看板
- 广告预算、搜索词、关键词和投放结构分析
- 基于审批的广告规则和半自动优化
- 更精细的补货预测、库存调拨和供应商绩效
- 头程物流对账、采购对账、请款与审批流
- 运营目标、任务、异常工单和通知中心
- 飞书/企业微信等内部消息与审批集成
- 自定义报表、指标中心和轻量 BI

### 4.3 P2：中长期演进

- AI 经营分析、异常归因和自然语言问数
- AI Listing 辅助、评论/退货原因分析
- 自动调价、自动预算和广告自动化（必须有风控、审批和回滚）
- 多平台、多公司主体、海外仓深度集成
- 移动端或小程序

## 5. 核心业务闭环

### 5.1 数据闭环

Amazon/内部数据源 → 原始数据层 → 标准化业务模型 → 业务单据 → 指标与报表 → 异常告警 → 人工处置 → 审计留痕。

### 5.2 供应链闭环

补货建议 → 采购计划 → 采购审批 → 下单 → 到货/质检 → 入库 → FBA 发货 → 在途 → FBA 上架 → 销售消耗 → 再补货。

### 5.3 财务闭环

销售订单 → Amazon 交易与费用 → 商品/采购成本 → 头程及其他费用分摊 → 利润计算 → 结算 → 回款核对 → 月度封账。

## 6. 技术架构建议

### 6.1 总体原则

- **模块化单体优先**：业务仍在成形阶段，先保证模块边界清晰、交付快、事务一致；达到明确容量或组织边界后再拆服务。
- **API 与数据同步解耦**：前台业务请求不直接等待 Amazon API；统一由异步任务同步并写入本地数据模型。
- **原始数据可追溯**：保留 Amazon 报告及关键 API 原始载荷，支持重算、补数和审计。
- **指标统一定义**：销量、收入、成本、利润、库存等指标必须有负责人、公式、来源和版本。

### 6.2 推荐技术栈

- 前端：Vue 3 + TypeScript + Vite + Pinia + 企业级组件库
- 后端：Java 21 + Spring Boot 3，按领域拆分模块
- 数据库：MySQL 8
- 缓存与任务协调：Redis
- 异步任务：首期使用可靠任务表/调度框架；吞吐量达到阈值后引入消息队列
- 文件与原始报表：S3 兼容对象存储
- 报表：业务库读模型起步；数据量增长后引入独立分析库/数仓
- 部署：Docker + CI/CD，环境分为开发、测试、预发布和生产
- 可观测性：集中日志、指标、链路、任务成功率和业务数据质量监控

### 6.3 领域模块

1. IAM 与组织权限
2. 店铺授权与渠道集成
3. 商品与主数据
4. 销售订单
5. 库存与仓储
6. 采购与供应商
7. FBA/物流
8. 成本、财务与结算
9. 指标、报表与预警
10. 审批、任务与审计

### 6.4 Amazon 集成重点

- 公司自用场景优先评估注册 **Private SP-API Application**。
- 授权、密钥和刷新令牌统一进入受保护的凭据存储，禁止进入代码、日志和普通配置文件。
- 针对 API 限流设计队列、退避、优先级和断点续传。
- 所有同步任务采用幂等键、水位线和对账机制。
- 同时支持事件通知、增量拉取、报告下载和人工补数。
- Amazon Ads API 与 SP-API 分开规划授权和数据模型。

## 7. 数据与安全治理

### 7.1 数据分层

- ODS：Amazon 原始 API/报告及内部导入文件
- Core：统一商品、订单、库存、采购、费用和结算模型
- Mart：销售、库存、利润、供应链及管理看板主题数据

### 7.2 数据质量

- 完整性：订单、交易、库存与报告是否缺失
- 唯一性：订单、交易、SKU 映射是否重复
- 一致性：订单金额与交易/结算、库存总量与流水是否一致
- 及时性：各数据源最近成功同步时间和延迟
- 可追溯性：报表指标可下钻到业务单据和原始来源

### 7.3 安全要求

- 最小权限、强制 RBAC、敏感操作二次确认
- Amazon 授权凭据加密存储和定期轮换
- PII/敏感数据分级、脱敏、导出控制和访问审计
- 财务封账、审批和关键配置变更必须留痕
- 生产数据库禁止开发人员日常直连修改
- 定期备份、恢复演练和灾难恢复预案

## 8. Sprint 与里程碑计划

> 以下周期为初步估算。每个 Sprint 开始前提交详细计划，经老板确认后执行；完成后必须通过演示、测试和数据验收才能进入下一 Sprint。

| Sprint | 参考周期 | 核心交付 | 退出条件 |
| --- | --- | --- | --- |
| Sprint 0：立项与需求基线 | 2 周 | 现状调研、流程图、角色权限、数据字典、MVP 范围、原型、SP-API 申请方案 | 核心岗位确认流程；老板确认 MVP 边界 |
| Sprint 1：技术底座 | 2 周 | 工程骨架、环境、CI/CD、登录/RBAC、审计、店铺配置、任务框架 | 四环境可部署；权限和审计通过验收 |
| Sprint 2：Amazon 数据接入 | 2～3 周 | 授权、订单/商品/库存/财务基础同步、原始数据层、任务监控 | 指定店铺连续稳定同步；可补数、可追溯 |
| Sprint 3：销售与库存 MVP | 2～3 周 | 主数据、订单中心、库存视图、销售看板、基础预警 | 关键数据与 Seller Central/原表对账达标 |
| Sprint 4：采购与 FBA | 3 周 | 采购、收货、入库、库存流水、补货建议、FBA 发货基础流程 | 选定 SKU 完成端到端试跑 |
| Sprint 5：财务与利润 | 3 周 | 成本、费用分摊、订单/SKU/店铺利润、结算回款、封账 | 财务选定月份完成对账并签字确认 |
| Sprint 6：联调与数据治理 | 2 周 | 异常补偿、数据质量看板、性能、安全、回归测试 | P0 缺陷清零；无阻断级风险 |
| Sprint 7：试点上线 | 2～3 周 | 试点店铺、用户培训、并行运行、反馈修复、上线方案 | 连续稳定运行；业务负责人批准切换 |

## 9. 验收指标

具体阈值在 Sprint 0 由业务、财务和技术共同确认，建议基线如下：

- P0 关键流程覆盖率：100%
- 订单/交易重复入库率：0
- 指定周期内订单、库存、结算数据完整率：≥ 99.9%
- 核心财务报表与人工核对差异：解释后净差异 ≤ 0.1%
- 同步任务成功率：≥ 99.5%，失败任务可自动或人工补偿
- 核心页面 P95 响应时间：≤ 2 秒（大报表和导出除外）
- 关键操作审计覆盖率：100%
- 试点岗位核心流程使用率：≥ 90%
- 月度人工报表工时下降：目标 ≥ 60%

## 10. 测试与上线策略

### 10.1 测试层次

- 单元测试：核算、库存和状态机等核心规则
- 集成测试：Amazon 适配器、数据库、缓存、任务与对象存储
- 契约测试：Amazon API/报告字段变化和内部接口
- 数据对账测试：按订单、SKU、店铺、结算周期逐层对账
- 端到端测试：采购到入库、FBA 发货、销售到结算
- 权限与安全测试：越权、导出、日志、凭据和审计
- 性能与恢复测试：批量同步、报表查询、任务重试和备份恢复

### 10.2 上线方式

1. 选择少量店铺、站点和核心岗位作为试点。
2. 新旧流程并行运行 2～4 周，不立即停用原 Excel/系统。
3. 每日自动对账，差异必须分类、定位和闭环。
4. 达到退出指标后分批扩大店铺与用户范围。
5. 财务数据至少完成一个结算周期验证后再作为正式口径。

## 12. 主要风险与应对

| 风险 | 影响 | 应对措施 |
| --- | --- | --- |
| 需求无限对标成熟 ERP | 项目范围失控、长期无法上线 | 坚持 P0/P1/P2；每项需求必须对应岗位、频次和收益 |
| Amazon 授权、限流或接口变化 | 数据接入延期或不稳定 | Sprint 0 提前申请；适配层隔离；限流、重试、补数和契约监控 |
| SKU/店铺/仓库主数据混乱 | 业务数据无法统一 | 上线前治理映射关系；设置主数据 Owner 和变更流程 |
| 利润口径不一致 | 财务不认可系统 | Sprint 0 先定公式；保留计算版本和明细追溯；按月并行对账 |
| 业务人员参与不足 | 系统与实际流程脱节 | 固定关键用户；每 Sprint 演示和 UAT；阻塞事项限时确认 |
| 一开始微服务化 | 研发和运维复杂度过高 | 模块化单体起步；依据容量和团队边界再拆分 |
| 自动化误操作 | 价格、广告或库存损失 | 初期只读或人工确认；审批、阈值、灰度、审计和回滚 |
| 内部系统安全被忽视 | 店铺、财务或客户数据泄露 | 最小权限、凭据托管、网络隔离、审计、备份和安全测试 |

## 13. 项目管理机制

- 每个 Sprint：计划评审 → 任务执行 → 联调/测试 → 成果核验 → 老板验收。
- 每周输出一次状态：已完成、进行中、阻塞、风险、需要决策。
- 需求变更统一进入 Backlog，不在 Sprint 中途无评估插入。
- 完成定义（DoD）：代码合并、评审通过、测试通过、文档更新、可部署、监控就绪、业务验收材料齐全。
- 重大决策记录：范围、架构、数据口径、安全和上线切换必须留痕。

## 14. 立项前需要确认的决策

1. 首期纳入多少店铺、哪些国家站点？
2. 业务模式包含 FBA、FBM，还是以 FBA 为主？
3. 当前采购、仓库、物流、财务分别使用哪些系统或 Excel？
4. 公司最痛的三个问题是什么：利润不准、库存不准、补货、对账、广告，还是协同？
5. 商品成本采用移动加权、FIFO、批次指定或其他规则？
6. 是否需要在 MVP 中纳入 Amazon Ads，还是放到 P1？
7. 目标部署环境、网络访问范围和预计用户数/店铺数/订单量？
8. 运营、供应链、财务三名关键用户由谁担任？

## 15. Sprint 0 建议任务

在本方案经老板确认后启动 Sprint 0：

1. 访谈管理层、运营、采购、仓库、物流和财务。
2. 收集现有 Excel、报表、系统清单和典型业务样本。
3. 绘制现状流程（As-Is）和目标流程（To-Be）。
4. 输出主数据字典及 SKU/MSKU/ASIN/FNSKU 映射规则。
5. 确认利润、库存、销量和回款指标口径。
6. 形成 P0 用户故事、原型、验收标准和需求追踪矩阵。
7. 完成 Amazon SP-API 应用类型、权限范围与申请材料评估。
8. 完成技术 Spike：授权、订单/库存/财务报告各跑通一条链路。
9. 输出架构决策记录、数据安全分级和 MVP 估算。
