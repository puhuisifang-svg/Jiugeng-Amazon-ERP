## 1. 目标与原则

- 对 MVP 的登录权限、产品/SKU、辅料及单仓库存、选品、公开店铺上新监控和五类导入提供分层验证。
- 每条 P0 需求必须可追溯到需求/权限基线、测试 ID、执行结果和可复核证据；测试设计完成不等于验收通过。
- 正常、异常、边界、重复/幂等、并发、权限越权和失败恢复均纳入核心用例。
- 前端可见性与后端鉴权分别验证；数据库唯一键、事务和幂等键必须作为应用校验的兜底。
- 测试数据使用伪造或脱敏样本；凭据仅使用 SecretRef/受保护变量，任何证据不得回显真实值。

## 3. 核心专项策略

### 3.1 人工编码与字段/模板一致性

- Product/SPU、内部 SKU、辅料编码必须由用户手工输入，系统和 Excel 导入均不得自动生成或补号。
- 以等价类和边界值验证：必填、trim、1/64/65 位、合法字符正则、中文/空格/特殊字符、大小写不敏感重复、批次内/跨批次/并发重复。
- 三类编码分别全局唯一；停用记录不物理删除、不误复用。已保存编码仅管理员可改，原因及前后值、人、时必须审计。
- 五类当前模板（产品、SKU、辅料、SKU—辅料关系、辅料期初库存）与字段字典、样例、UI、API DTO 和数据库迁移做契约比对。

### 3.2 三角色可见性与越权

- 依据权限矩阵逐资源验证系统管理员、产品/辅料人员、选品人员的管理/操作/查看/无权限。
- 分别检查菜单、按钮和直接 URL；隐藏无权入口后，仍需直接调用读写 API，验证 401/403 或等效拒绝。
- 覆盖篡改角色、对象 ID、HTTP 方法和批量接口；无权请求不得产生业务写入或审计之外的副作用。
- 产品/辅料人员与选品人员只能查看本人操作审计；普通用户不得修改审计。三类角色默认均不可查看密钥值。

### 3.3 五类导入校验

- 流程为“上传→校验→预览→确认提交→结果下载”；确认前业务表和库存余额必须零写入。
- 失败必须逐行返回工作表、行号、字段和原因；覆盖缺必填、非法格式/枚举、重复、引用不存在、父子关系不一致和混合成功/失败批次。
- 输入数据行数必须等于成功、失败和明确跳过行数之和，禁止静默丢数。
- 重复确认、网络重试和并发提交不得重复新增或重复记期初；记录来源、批次、操作人、时间、结果文件和审计事件。

### 3.4 选品查重与可追溯

- 美国站候选有 ASIN 时按 `marketplace_id + ASIN` 查重；未解析 ASIN 时按标准化 URL 暂存查重。
- 手工录入与监控事件进入同一候选池；重复提交、重试和并发不得产生重复候选。
- 监控来源候选必须保留店铺、快照/新品事件和发现时间引用；状态只能按“待评估→评估中→通过/淘汰”流转，淘汰原因按规则必填并审计。

### 3.5 监控首次基线、失败保护与新品去重

- 首个通过完整性校验的成功快照只建立基线，不把基线已有商品生成新品事件。
- 完整性至少核对任务成功状态、分页闭合、声明数量与实际项目数、ASIN 唯一/格式、证据引用及 hash。
- 采集失败、空结果、分页不完整、关键字段缺失或重复异常的快照保留任务/错误证据，但不得晋升或覆盖最近有效基线。
- 后续完整快照按 ASIN 集合差异生成疑似新品；以“监控店铺 + marketplace + ASIN”唯一，重跑、重试和并发只产生一次首发事件；不同店铺互不串基线或误去重。
- 连续 7 天从首个有效快照起算；报告需给出合规、覆盖、完整性、稳定性、成本、成功率、误报和人工导入降级结论。

### 3.6 库存一致性、工程与安全门禁

- 库存余额与流水在同一事务中写入，重复业务请求不得重复记账，负库存拦截率和余额/流水一致率均为 100%。
- 前端按 `pnpm-lock.yaml` 干净安装并通过 lint/test/build；后端使用 Java 21 与 Maven Wrapper 干净通过 test/package 和 Flyway 空库迁移。
- Compose 验证依赖健康以及 MySQL/对象存储在容器重启、保留命名卷重建后持久；Redis 按其“仅可重建状态”声明验证。
- CI 必须真实执行前后端构建/测试、依赖及敏感信息扫描；故意失败实验应能阻断，工作树、Git 历史、日志和产物均不得含真实凭据。

## 4. 明确后置范围

以下能力不属于当前精简 MVP，不纳入本期通过率、发布准入或端到端验收：StoreAccount、店铺 Listing 映射及导入、采购、生产、成品库存、FBA 发货流程、销售订单/销售到回款、财务交易与结算、成本/利润、广告、多层 BOM、多仓、批次/效期、多站点及 5 店 SP-API 自动同步。

若后续经批准纳入范围，必须先更新 PRD、验收标准、追踪矩阵和测试数据，再设计对应单元、集成、数据对账和端到端测试；不得沿用本期结果宣称通过。

## 5. 环境、数据与证据

- Local/CI 用伪造数据；Test/UAT 使用批准的 20～50 条脱敏业务样本；非生产环境不得使用未脱敏生产个人信息。
- 每次执行记录版本/提交、环境、时间、测试 ID、前置数据、实际结果、缺陷 ID 和结论。
- 证据可为命令与退出码、JUnit/扫描报告、已脱敏 API 请求响应、数据库核对、截图、快照 hash/基线 ID/任务 ID。
- `Pass` 必须有证据；`N/A` 必须有批准记录。失败或阻塞必须有 Owner、期限和回归结果。

## 6. 缺陷分级与发布准入

- P0：数据破坏、越权读写、真实凭据泄露、失败快照覆盖有效基线或核心发布链路完全阻断；立即单独上报 PJM。
- P1：核心规则错误、静默丢数、去重失效、持久化丢失、CI 未阻断或基线冲突；未批准不得遗留。
- P2：不影响数据和核心门禁的非核心异常、文案/布局或证据完整性问题。

发布/试点准入：

1. Approved P0 需求动态覆盖率 100%，P0=0，P1 无未批准遗留。
2. 权限、审计、编码、导入、库存、选品去重及监控失败保护专项通过。
3. 普通列表 P95 ≤2 秒；1,000 行导入 ≤5 分钟；库存一致率 100%。
4. 自动监控仅在批准数据源完成连续 7 天且成功率 ≥95%、人工复核误报率 <5% 后准入；否则按批准的人工导入降级范围验收。
5. 干净构建、Compose 持久化、CI/敏感扫描和备份恢复证据可复核。
6. QA 出具测试报告，业务 Owner 完成 UAT，PJM 核验证据，最终由老板验收。
